# S3

Set up the S3 destination connector by following this guide.

## Prerequisites

1. Allow connections from Airbyte to your AWS S3/Minio S3 cluster if they use separate VPCs.
   If you're using Airbyte Cloud with IP-based access controls, add Airbyte's [IP addresses](/platform/operating-airbyte/ip-allowlist) to your allowlist.
2. [Enforce encryption of data in transit](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html#transit).
3. Prepare an S3 bucket with one of these authentication methods:
   - Credentials
   - A Role ARN
   - An instance profile with host read/write permissions configured for EC2 or EKS

    - You always need these fields:

      - **S3 Bucket Name**
      - **S3 Bucket Path**
      - **S3 Bucket Region**

    - For STS Assume Role, provide:

      - **Role ARN**

    - For AWS credentials, provide:

      - **Access Key ID**
      - **Secret Access Key**

    - For an Instance Profile, you can omit the Access Key ID, Secret Access Key, and Role ARN.

## Setup

### Step 1: Set up S3

[Sign in](https://console.aws.amazon.com/iam/) to your AWS account.

Prepare the S3 bucket you'll use as the destination. See [this](https://docs.aws.amazon.com/AmazonS3/latest/userguide/create-bucket-overview.html) to create an S3 bucket.

NOTE: Without TLS, the Amazon S3 connection silently reverts to an unencrypted connection.
Airbyte recommends configuring every connection to use TLS/SSL because of AWS's [shared responsibility model](https://aws.amazon.com/compliance/shared-responsibility-model/)

#### Create a bucket policy

1. Open the [IAM console](https://console.aws.amazon.com/iam/home#home).
2. In the IAM dashboard, select **Policies**, then click **Create Policy**.
3. Select the **JSON** tab, then paste the following JSON into the Policy editor.
   Replace the example bucket name with your bucket name.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:DeleteObject",
        "s3:PutObjectAcl",
        "s3:ListBucket",
        "s3:ListBucketMultipartUploads",
        "s3:AbortMultipartUpload",
        "s3:GetBucketLocation"
      ],
      "Resource": [
        "arn:aws:s3:::YOUR_BUCKET_NAME/*",
        "arn:aws:s3:::YOUR_BUCKET_NAME"
      ]
    }
  ]
}
```

:::note
Object-level permissions alone can't currently authenticate the connection. Include the **bucket-level** permissions shown in the example above.
:::

4. Give your policy a descriptive name, then click **Create policy**.

With the default S3 Path Format `${NAMESPACE}/${STREAM_NAME}/${YEAR}_${MONTH}_${DAY}_${EPOCH}_`, the full output data path is:

```text
<bucket-name>/<source-namespace-if-exists>/<stream-name>/<upload-date>_<epoch>_<partition-id>.<format-extension>
```

For example:

```text
testing_bucket/data_output_path/public/users/2021_01_01_1234567890_0.csv.gz
↑              ↑                ↑      ↑     ↑          ↑          ↑ ↑
|              |                |      |     |          |          | format extension
|              |                |      |     |          |          unique incremental part id
|              |                |      |     |          milliseconds since epoch
|              |                |      |     upload date in YYYY_MM_DD
|              |                |      stream name
|              |                source namespace (if it exists)
|              bucket path
bucket name
```

This naming pattern provides these benefits:

1. Each stream has its own directory.
2. You can sort the data output files by upload time.
3. The upload time combines date and milliseconds, making it readable and unique.

You can further customise the bucket path with these available variables:

- `${NAMESPACE}`: Namespace where the stream originates, or the namespace configured through the connection namespace fields.
- `${STREAM_NAME}`: Stream name.
- `${YEAR}`: Year when the sync wrote the output data.
- `${MONTH}`: Month when the sync wrote the output data.
- `${DAY}`: Day when the sync wrote the output data.
- `${HOUR}`: Hour when the sync wrote the output data.
- `${MINUTE}` : Minute when the sync wrote the output data.
- `${SECOND}`: Second when the sync wrote the output data.
- `${MILLISECOND}`: Millisecond when the sync wrote the output data.
- `${EPOCH}`: Milliseconds since Epoch when the sync wrote the output data.
- `${UUID}`: Random uuid string.
- `${SYNC_ID}`: ID of the sync job that wrote the output data.

Note:

- Multiple `/` characters in the S3 path collapse into one `/` character.

The stream name can include a prefix if you've configured one on the connection.
A data sync can create multiple files because output files are partitioned by size.
Each compressed file targets a size of 200MB or less.

## Supported sync modes

| Sync mode | Supported? |
| :--- | :--- |
| [Full Refresh - Overwrite](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/full-refresh-overwrite) | Yes |
| [Full Refresh - Append](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/full-refresh-append) | Yes |
| [Full Refresh - Overwrite + Deduped](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/full-refresh-overwrite-deduped) | No |
| [Incremental Sync - Append](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/incremental-append) | Yes |
| [Incremental Sync - Append + Deduped](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/incremental-append-deduped) | No |

The Airbyte S3 destination syncs data to AWS S3 or Minio S3.
It writes each stream to its own directory under the bucket.

⚠️ In "Full Refresh Overwrite Sync" mode, a successful sync retains data from the same generation.
It deletes all data from previous generations.
If a sync fails between generations, data from multiple generations can remain until a later sync succeeds.
Each S3 object uses the `x-amz-meta-ab-generation-id` tag to identify its generation.
Airbyte recommends a dedicated S3 resource for this sync. This reduces accidental data deletion caused by misconfiguration. ⚠️

## Supported output schema

Each stream outputs to its own directory, based on your configuration.
The stream's complete datastore includes every output file in that directory.
You can treat the directory as the equivalent of a database table.

- In Full Refresh Sync mode, old output files are purged before new files are created.
- In Incremental - Append Sync mode, new output files contain only the new data.

### Avro

[Apache Avro](https://avro.apache.org/) serialises data in a compact binary format.
The Airbyte S3 Avro connector always uses the [binary encoding](https://avro.apache.org/docs/1.12.0/specification/#binary-encoding) and assumes every data record follows the same schema.

#### Configuration

Choose from these compression codecs:

- No compression
- `deflate`
  - Compression level
    - Range `[0, 9]`. The default is 0.
    - Level 0: no compression and fastest.
    - Level 9: best compression and slowest.
- `bzip2`
- `xz`
  - Compression level
    - Range `[0, 9]`. The default is 6.
    - Levels 0-3 are fast with medium compression.
    - Levels 4-6 are fairly slow with high compression.
    - Levels 7-9 work like level 6 but use larger dictionaries and need more memory.
      Presets 7, 8, and 9 waste memory unless the uncompressed file exceeds 8 MiB, 16 MiB, and 32 MiB, respectively.
- `zstandard`
  - Compression level
    - Range `[-5, 22]`. The default is 3.
    - Negative levels are 'fast' modes similar to `lz4` or `snappy`.
    - Levels above 9 are generally for archival purposes.
    - Levels above 18 use considerable memory.
  - Include checksum
    - Set this to `true` to include a checksum in each data block.
- `snappy`

#### Data schema

An Airbyte data stream in JSON schema is first converted to an Avro schema.
The JSON object is then converted to an Avro record.
Data streams can come from any source, so JSON-to-Avro conversion has arbitrary rules and limitations.
Learn more about source data conversion to Avro and the current limitations [here](https://docs.airbyte.com/understanding-airbyte/json-avro-conversion).

### CSV

Like most other Airbyte destination connectors, the output usually has three columns.
These are a UUID, an emission timestamp, and the data blob.
With CSV output, you can normalise \(flatten\) the data blob into multiple columns.

| Column                   | Condition                                                                                          | Description                                                                 |
| :----------------------- | :------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------- |
| `_airbyte_raw_id`        | Always exists.                                                                                     | A uuid assigned by Airbyte to each processed record.                        |
| `_airbyte_extracted_at`  | Always exists.                                                                                     | A timestamp representing when the event was extracted from the data source. |
| `_airbyte_generation_id` | Always exists.                                                                                     | An integer id that increases with each new refresh.                         |
| `_airbyte_meta`          | Always exists.                                                                                     | A structured object containing metadata about the record.                   |
| `_airbyte_data`          | When no normalization \(flattening\) is needed, all data resides under this column as a JSON blob. |                                                                             |
| root level fields        | When root level normalization \(flattening\) is selected, the root level fields are expanded.      |                                                                             |

The schema for `_airbyte_meta` is:

| Field Name | Type    | Description                             |
| :--------- | :------ | :-------------------------------------- |
| `changes`  | list    | A list of structured change objects.    |
| `sync_id`  | integer | An integer identifier for the sync job. |

The schema for a change object is:

| Field Name | Type   | Description                                                                                                              |
| :--------- | :----- | :----------------------------------------------------------------------------------------------------------------------- |
| `field`    | string | The name of the field that changed.                                                                                      |
| `change`   | string | The type of change (eg, `NULLED`, `TRUNCATED`).                                                                          |
| `reason`   | string | The reason for the change, including its system of origin (ie, whether it was a source, destination, or platform error). |

For example, consider this JSON object from a source:

```json
{
  "user_id": 123,
  "name": {
    "first": "John",
    "last": "Doe"
  }
}
```

Without normalisation, the output CSV is:

| `_airbyte_raw_id`                      | `_airbyte_extracted_at` | `_airbyte_generation_id` | `_airbyte_meta`                     | `_airbyte_data`                                                |
| :------------------------------------- | :---------------------- | :----------------------- | ----------------------------------- | :------------------------------------------------------------- |
| `26d73cde-7eb1-4e1e-b7db-a4c03b4cf206` | 1622135805000           | 11                       | `{"changes":[], "sync_id": 10111 }` | `{ "user_id": 123, name: { "first": "John", "last": "Doe" } }` |

With root-level normalisation, the output CSV is:

| `_airbyte_raw_id`                      | `_airbyte_extracted_at` | `_airbyte_generation_id` | `_airbyte_meta`                     | `user_id` | `name.first` | `name.last` |
| :------------------------------------- | :---------------------- | :----------------------- | ----------------------------------- | :-------: | :----------: | :---------: |
| `26d73cde-7eb1-4e1e-b7db-a4c03b4cf206` | 1622135805000           | 11                       | `{"changes":[], "sync_id": 10111 }` |    123    |     John     |     Doe     |

You can compress output files. GZIP compression is the default.
When you select compression, the output filename gains an extra extension (GZIP: `.csv.gz`).

### JSON Lines \(JSONL\)

[JSON Lines](https://jsonlines.org/) is a text format containing one JSON object per line. Each line uses this structure:

```json
{
  "_airbyte_raw_id": "<uuid>",
  "_airbyte_extracted_at": "<timestamp>",
  "_airbyte_generation_id": "<generation-id>",
  "_airbyte_meta": "<json-meta>",
  "_airbyte_data": "<json-data-from-source>"
}
```

For example, consider these two JSON objects from a source:

```json
[
  {
    "user_id": 123,
    "name": {
      "first": "John",
      "last": "Doe"
    }
  },
  {
    "user_id": 456,
    "name": {
      "first": "Jane",
      "last": "Roe"
    }
  }
]
```

They appear in the output file as follows:

```text
{ "_airbyte_raw_id": "26d73cde-7eb1-4e1e-b7db-a4c03b4cf206", "_airbyte_extracted_at": "1622135805000", "_airbyte_generation_id": "11", "_airbyte_meta": { "changes": [], "sync_id": 10111 }, "_airbyte_data": { "user_id": 123, "name": { "first": "John", "last": "Doe" } } }
{ "_airbyte_raw_id": "0a61de1b-9cdd-4455-a739-93572c9a5f20", "_airbyte_extracted_at": "1631948170000", "_airbyte_generation_id": "12", "_airbyte_meta": { "changes": [], "sync_id": 10112 }, "_airbyte_data": { "user_id": 456, "name": { "first": "Jane", "last": "Roe" } } }
```

You can compress output files. GZIP compression is the default.

### Parquet

#### Configuration

Configure the Parquet output with these settings:

| Parameter                 |  Type   |    Default     | Description                                                                                                                                                                                                                       |
| :------------------------ | :-----: | :------------: | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `compression_codec`       |  enum   | `UNCOMPRESSED` | **Compression algorithm**. Available candidates are: `UNCOMPRESSED`, `SNAPPY`, `GZIP`, `LZO`, `BROTLI`, `LZ4`, and `ZSTD`.                                                                                                        |
| `block_size_mb`           | integer |   128 \(MB\)   | **Block size \(row group size\)** in MB. This is the size of a row group being buffered in memory. It limits the memory usage when writing. Larger values will improve the IO when reading, but consume more memory when writing. |
| `max_padding_size_mb`     | integer |    8 \(MB\)    | **Max padding size** in MB. This is the maximum size allowed as padding to align row groups. This is also the minimum size of a row group.                                                                                        |
| `page_size_kb`            | integer |  1024 \(KB\)   | **Page size** in KB. The page size is for compression. A block is composed of pages. A page is the smallest unit that must be read fully to access a single record. If this value is too small, the compression will deteriorate. |
| `dictionary_page_size_kb` | integer |  1024 \(KB\)   | **Dictionary Page Size** in KB. There is one dictionary page per column per row group when dictionary encoding is used. The dictionary page size works like the page size but for dictionary.                                     |
| `dictionary_encoding`     | boolean |     `true`     | **Dictionary encoding**. This parameter controls whether dictionary encoding is turned on.                                                                                                                                        |

These parameters relate to the `ParquetOutputFormat`. See [Java doc](https://www.javadoc.io/doc/org.apache.parquet/parquet-hadoop/1.12.0/org/apache/parquet/hadoop/ParquetOutputFormat.html) for more details.
Also see [Parquet documentation](https://parquet.apache.org/docs/file-format/configurations/) for the recommended settings: 512 - 1024 MB block size and 8 KB page size.

#### Data schema

An Airbyte data stream in JSON schema is first converted to an Avro schema.
The JSON object is then converted to an Avro record.
Finally, the Avro record is output in Parquet format.
Data streams can come from any source, so JSON-to-Avro conversion has arbitrary rules and limitations.
Learn more about source data conversion to Avro and the current limitations [here](https://docs.airbyte.com/understanding-airbyte/json-avro-conversion).
