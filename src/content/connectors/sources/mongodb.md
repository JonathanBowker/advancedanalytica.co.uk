# MongoDB

Airbyte's certified MongoDB connector gives you these features:

- [Change Data Capture (CDC)](https://docs.airbyte.com/understanding-airbyte/cdc) using MongoDB [change streams](https://www.mongodb.com/docs/manual/changeStreams/), read directly with the MongoDB driver.
- Full refresh and incremental sync modes for every collection.
- Reliable replication for collections of any size with [checkpointing](https://docs.airbyte.com/understanding-airbyte/airbyte-protocol/#state--checkpointing). Interrupted syncs resume from the last checkpointed document instead of restarting.
- Choose a discovered schema, with fields sampled from your documents, or schemaless mode, which syncs each document as one JSON object.

In version 3.0.0, this connector's Docker image changed from `airbyte/source-mongodb-v2` to `airbyte/source-mongodb`. The connector definition remains unchanged.

This page covers setup, replication and reference information, including data type mapping, configuration parameters and the changelog. If you're upgrading from version 2.x, read [migration guide](https://docs.airbyte.com/integrations/sources/mongodb-migrations) first.

## Quick start

Set up a MongoDB source in four steps:

1. [Create a dedicated read-only MongoDB user](#step-1-create-a-dedicated-read-only-mongodb-user).
2. [Find the connection string](#step-2-find-the-mongodb-cluster-connection-string) of your [replica set](https://www.mongodb.com/docs/manual/replication/) or [sharded cluster](https://www.mongodb.com/docs/manual/sharding/), hosted on [MongoDB Atlas](https://www.mongodb.com/atlas/database) or self-hosted.
3. [Create the MongoDB source](#step-3-configure-the-airbyte-mongodb-source) in Airbyte.
4. [Allow inbound traffic from Airbyte](#step-4-allow-inbound-traffic-from-airbyte) if your cluster restricts incoming connections.

### Requirements

- A **replica set** or a **sharded cluster** connected through `mongos`. A standalone `mongod` has no oplog or change streams. Full Refresh works, but Incremental sync fails when the change stream opens. A single-node replica set works for development. See [Convert a Standalone to a Replica Set](https://www.mongodb.com/docs/manual/tutorial/convert-standalone-to-replica-set/).
- MongoDB 4.4 or later. The connector is tested against MongoDB 7.0. Deletes include the deleted document only with MongoDB 6.0 or later and [pre-images](https://www.mongodb.com/docs/manual/changeStreams/#change-streams-with-document-pre-and-post-images) enabled on the collection.
- On MongoDB Atlas, a dedicated cluster at M10 tier or above. Shared tiers M0, M2 and M5 don't support required operations and may fail during connection setup.
- An oplog large enough to cover the gap between syncs, with extra capacity. See [MongoDB Oplog and Change Streams](https://docs.airbyte.com/integrations/sources/mongodb/mongodb-troubleshooting#mongodb-oplog-and-change-streams).

### Step 1: Create a read-only MongoDB user

Create a dedicated, read-only user to replicate data. You can use an existing MongoDB user with the privileges described below. A dedicated user helps you identify connector activity in logs. You can also revoke its access without affecting anything else.

The required privileges depend on how many databases you configure:

| Databases configured | Required privileges                                                                                                                                                                                                                                                                                             |
| :------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One                  | The built-in [`read`](https://www.mongodb.com/docs/manual/reference/built-in-roles/#mongodb-authrole-read) role on that database. The change stream is opened on the database itself, so no cluster-wide privilege is needed.                                                                                   |
| Several              | [`readAnyDatabase`](https://www.mongodb.com/docs/manual/reference/built-in-roles/#mongodb-authrole-readAnyDatabase) (on Atlas: the **Only read any database** built-in role). Changes from several databases are read through one cluster-wide change stream, which requires read privileges on every database. |

In either case, the connector only needs read access. It never writes to your cluster or reads the `local` or `config` databases.

#### MongoDB Atlas

1. Log in to the [MongoDB Atlas dashboard](https://cloud.mongodb.com/).
2. From the dashboard, click "Database Access" under "Security".

   ![Security Database Access](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_step_2.png)

3. Click the "+ ADD NEW DATABASE USER" button.

   ![Add New Database User](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_step_3.png)

4. In the "Add new Database User" modal, choose "Password" for the "Authentication Method".

   ![Authentication Method](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_step_4.png)

5. In "Password Authentication", enter `READ_ONLY_USER` or your chosen username in the first text box. Enter a password in the second. You'll enter both in the Airbyte source during Step 3.

   ![Username and Password](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_step_5.png)

6. Under "Database User Privileges", grant read access in one of two ways:

   - Under "Built-in Role", click "Select one built-in role for this user" and choose "Only read any database".

     ![Database User Privileges](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_step_6.png)

   - Alternatively, under "Specific Privileges", click "Add Specific Privilege" and add `readAnyDatabase`.

     ![Read Database Privileges](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_read_permission.png)

:::info
Both options grant `readAnyDatabase`, which you need when configuring multiple databases. For one database with narrower privileges, use a [custom role](https://www.mongodb.com/docs/atlas/security-add-mongodb-roles/) with the `read` role on that database.
:::

7. Enable "Restrict Access to Specific Clusters/Federated Database instances". Select only the cluster you want to replicate.

   ![Restrict Access](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_step_7.png)

8. Click "Add User" at the bottom to save the user.

   ![Add User](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_database_user_step_8.png)

#### Self-hosted

These instructions use the [MongoDB shell](https://www.mongodb.com/docs/mongodb-shell/) (`mongosh`). To install it, follow [these instructions](https://www.mongodb.com/docs/mongodb-shell/install/#std-label-mdb-shell-install).

1. In a terminal, connect to the cluster as a user who can create users. For example, use one with the `userAdminAnyDatabase` role:

   ```shell
   > mongosh "<connection string to cluster>" --username <user with admin permissions>
   ```

2. Switch to the `admin` database:

   ```shell
   test> use admin
   switched to db admin
   ```

3. Create the `READ_ONLY_USER` user, or choose another name. To sync one database, grant it the `read` role:

   ```shell
   admin> db.createUser({user: "READ_ONLY_USER", pwd: "READ_ONLY_PASSWORD", roles: [{role: "read", db: "TARGET_DATABASE"}]})
   ```

   To sync multiple databases, grant `readAnyDatabase` instead:

   ```shell
   admin> db.createUser({user: "READ_ONLY_USER", pwd: "READ_ONLY_PASSWORD", roles: [{role: "readAnyDatabase", db: "admin"}]})
   ```

:::note
Replace `READ_ONLY_PASSWORD` with your chosen password and `TARGET_DATABASE` with the database you want to replicate. Create the user in the `admin` database. The connector authenticates against `admin`.
:::

4. Ensure every replica set member, or every `mongos`, requires authentication. Each must accept connections from Airbyte's network. Check these keys in each member's [configuration file](https://www.mongodb.com/docs/manual/reference/configuration-options/), which is `/etc/mongod.conf` on most Linux distributions. Restart the process after making changes:

   ```yaml
   net:
     bindIp: localhost,<the interface Airbyte reaches this member on>

   security:
     authorization: enabled
   ```

:::note
`net.bindIp` lists the interfaces the member listens on. `0.0.0.0` accepts connections from every interface. If you use it, restrict access with a firewall or the Step 4 IP allow list. `security.authorization: enabled` makes the member reject unauthenticated clients. Replica set members must also authenticate with each other using a keyfile or x.509 certificates. See [Internal/Membership Authentication](https://www.mongodb.com/docs/manual/core/security-internal-authentication/).
:::

### Step 2: Find the cluster connection string

#### MongoDB Atlas

Atlas is MongoDB's [cloud-hosted offering](https://www.mongodb.com/atlas/database). To find an Atlas-hosted cluster's connection string:

1. Log in to the [MongoDB Atlas dashboard](https://cloud.mongodb.com/).
2. From the dashboard, click the source cluster's "Connect" button.

   ![Connect to Source Cluster](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_connection_string_step_2.png)

3. In the "Connect to &lt;cluster name&gt;" modal, select "Shell" under "Access your data through tools".

   ![Shell Connect](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_connection_string_step_3.png)

4. Copy the connection string from "2. Run your connection string in your command line" in the modal.

   ![Copy Connection String](https://docs.airbyte.com/.gitbook/assets/source/mongodb/mongodb_atlas_connection_string_step_4.png)

The string looks like `mongodb+srv://cluster0.abcde.mongodb.net/`. Paste it exactly as Atlas displays it. The connector removes surrounding quotation marks and the `<username>:<password>@` placeholder. Enter credentials in the source's **Username** and **Password** fields instead. The password is then stored as a secret. Atlas connections always use TLS.

#### Self-hosted cluster

See [MongoDB connection string documentation](https://www.mongodb.com/docs/manual/reference/connection-string/#find-your-self-hosted-deployment-s-connection-string) to find a self-hosted deployment's connection string. List every replica set member or each sharded cluster's `mongos` router. This list lets the connector fail over when a member is unavailable. For example, use `mongodb://host1:27017,host2:27017,host3:27017/?replicaSet=rs0`. DNS seed lists (`mongodb+srv://`) also work.

The connector honours connection string options. In particular:

- Add `tls=true` to connect over TLS. See [Configure mongod and mongos for TLS/SSL](https://www.mongodb.com/docs/manual/tutorial/configure-ssl/).
- Set `readPreference` to choose which members serve reads. Without this option, the connector uses `secondaryPreferred`. This reads the initial snapshot and change stream from an available secondary, leaving the primary for your application.
- Set `compressors` to choose how the cluster's traffic is compressed. Without this option, the connector requests `snappy`, then `zlib`. It uses the first option the cluster supports. An empty `compressors=` disables compression.
- You can embed credentials as `mongodb://user:password@host…`, but the **Username** and **Password** fields are preferred. The connection string is stored in clear text, while the password field is stored as a secret. When you set both, the fields take precedence.

### Step 3: Configure the MongoDB source

In Airbyte, go to **Sources**, click **+ New source** and choose **MongoDB**. Then complete these fields:

1. **Cluster Type**: MongoDB Atlas or self-hosted.
2. **Connection String**: the string from Step 2.
3. **Database Names**: the databases containing the collections you want to sync. Add one name per entry. Multiple databases require the `readAnyDatabase` privilege from Step 1.
4. **Username** and **Password**: the user from Step 1. These fields are required for Atlas. For self-hosted clusters, leave them empty only when authentication isn't required.
5. **Schema Enforced**: leave it enabled unless your documents don't share a structure. See [Schema Enforcement](#schema-enforcement).

Keep the default advanced settings unless you need to change them. See [Configuration Parameters](#configuration-parameters) for details.

Click **Set up source**. Airbyte tests the connection before saving. It checks the cluster is reachable with your credentials and the user can list collections in configured databases. If the user can't read a database, the error names it. A standalone server passes with a log warning, but its Incremental syncs fail. Airbyte then discovers the collections. When **Schema Enforced** is enabled, it samples documents to build the schema. See [Schema Enforcement](#schema-enforcement). Discovery can take several minutes on clusters with many collections.

### Step 4: Allow inbound Airbyte traffic

If your cluster only accepts known addresses, allow the relevant Airbyte addresses:

- **Airbyte Cloud**: add the [Airbyte Cloud IP addresses](https://docs.airbyte.com/platform/operating-airbyte/ip-allowlist) to your allow list. In Atlas, use **Network Access** under **Security**.
- **Self-managed Airbyte**: allow the addresses of machines or Kubernetes nodes running your Airbyte workers.

## Replication methods

Each collection is a stream you can sync in **Full Refresh** or **Incremental** mode.

### Full Refresh

Each full refresh reads the entire collection, ordered by `_id`. The connector checkpoints progress after roughly every gigabyte of documents. If a sync fails partway through, it continues from the last checkpointed `_id` instead of restarting. A network error can cause this failure, for example.

### Incremental (CDC)

An incremental sync runs in two phases:

1. **Initial snapshot.** The first sync reads the entire collection, ordered by `_id` and checkpointed as described above. Before the snapshot, the connector records the current change stream position. This prevents changes during a long initial load from being lost. The next sync replays them.
2. **Change streams.** Later syncs resume the change stream from its saved position. They emit every insert, update, replace and delete made before the sync started. An update record contains the document's state when the event is read, using MongoDB's `updateLookup`. Therefore, several rapid updates can all show the final state. The next sync collects changes made while the current sync runs. This prevents a busy cluster from keeping a sync open indefinitely. Delete records have `_ab_cdc_deleted_at` set. They include the deleted document when the collection [stores pre-images](https://www.mongodb.com/docs/manual/changeStreams/#change-streams-with-document-pre-and-post-images) on MongoDB 6.0 or later. Otherwise, they include only its `_id`. If an updated document is deleted before the connector reads it back, the update is emitted as a delete.

To understand how Airbyte implements CDC, see [Change Data Capture (CDC)](https://docs.airbyte.com/understanding-airbyte/cdc/).

Change streams use the [replica set oplog](https://www.mongodb.com/docs/manual/core/replica-set-oplog/), which retains changes for a limited period. If the saved position has left the oplog, the sync fails or restarts. The **Invalid CDC position behavior** setting controls this behaviour. Long initial snapshots are protected automatically. A snapshot running longer than 8 hours pauses, saves its progress and retries. The retry reads the change stream before resuming the snapshot from its saved position. See [MongoDB Oplog and Change Streams](https://docs.airbyte.com/integrations/sources/mongodb/mongodb-troubleshooting#mongodb-oplog-and-change-streams) for oplog sizing guidance.

Every incremental record includes three metadata fields. `_ab_cdc_updated_at` contains a change-stream event's change time or a snapshot row's sync time. `_ab_cdc_deleted_at` is set for deletes. `_ab_cdc_cursor` contains the stream cursor. This is a change event's oplog time or the saved change-stream position for a snapshot row. Therefore, a later change always supersedes the row it replaces.

### Requirements for the `_id` field

The connector orders and resumes reads using `_id`. Keep these requirements in mind:

- **Use one BSON type for `_id` throughout a collection.** Integers, longs, doubles and decimals count as one type. MongoDB sorts `_id`s by type before value. A resumed read continues only with the checkpointed type. A collection mixing types, such as integer and string `_id`s, is fully read if uninterrupted. After a checkpoint, documents with other types aren't synced. When the collection read starts, the connector logs `The _id fields in this collection are not consistently typed, which may lead to data loss` with the types found. Make the `_id` type consistent or exclude the collection from the connection.
- Checkpoints are exact for every `_id` type. These include `ObjectId`, string, integer, long, double, decimal, date, timestamp, binary, embedded document and remaining BSON types. Binary includes UUIDs.

## Schema enforcement

By default, the connector enforces a schema. During setup and each schema refresh, it samples a configurable number of documents from every collection. It collects top-level fields and infers each field's type. You can then deselect fields in the connection's replication settings. The server returns only fields included in the schema.

The schema is inferred, not declared. Keep these points in mind:

- A field missing from sampled documents isn't included in the schema. It won't sync until you refresh the schema.
- When a field contains different types, the schema uses the first type found. Values are still emitted in their original types. For example, a string remains a string in a field typed `number`. Typed destinations may reject the value, causing it to arrive as `null`. Schemaless mode is better for these collections.
- Empty collections have no fields to sample, so they aren't discovered.
- [Views](https://www.mongodb.com/docs/manual/core/views/) and [time series collections](https://www.mongodb.com/docs/manual/core/timeseries-collections/) aren't synced or discovered. MongoDB provides no change streams for either. Time series collections also lack a `_id` index for checkpointing and resuming snapshots. For a view, sync its underlying collection instead.

When **Schema Enforced** is disabled, collections use schemaless mode. This mode doesn't assume documents share a structure. Each document creates a record with exactly two top-level fields:

```json
{
  "_id": <document id>,
  "data": {<the whole document, _id included>}
}
```

The contents of `data` vary by document. No field is omitted and no document is rejected. A field can be a string in one record and an object in the next. You can't deselect fields in schemaless mode. Schema discovery is lighter because sampling only identifies the type of `_id`.

### Array type normalisation

Most destinations can safely cast between primitive types, such as integer to string. They can't reconcile composite types, such as an object and an array. Without normalisation, records with this mismatch would be written as `NULL` in the destination. In schema-enforced mode, the connector handles fields with a schema type of `array`. It wraps each non-array value in a one-element array.

```javascript
// Document 1 - Array (matches schema)
{ "reviews": [{"rating": "A"}, {"rating": "B"}] }

// Document 2 - Single object (auto-wrapped)
{ "reviews": {"rating": "A"} }  →  { "reviews": [{"rating": "A"}] }
```

:::info
This normalisation handles occasional type inconsistencies. If your collection's fields change types frequently, consider schemaless mode instead.
:::

## Limitations and troubleshooting

For connector limitations and MongoDB connector troubleshooting, see [in our MongoDB troubleshooting guide](https://docs.airbyte.com/integrations/sources/mongodb/mongodb-troubleshooting).

### Schema discovery performance

:::warning
Schema discovery runs aggregation queries against your MongoDB cluster **in parallel across all collections** of a database. Production clusters with many collections or large documents can experience significant resource pressure. Effects can include degraded query performance, replication lag and, in extreme cases, cluster instability.
:::

MongoDB collections are schemaless, so no sample size guarantees a complete or stable schema. New fields can appear in documents at any time. With schema enforcement enabled, Discover runs `$sample` aggregation pipelines against every collection in the configured databases **in parallel**. These concurrent queries can place significant pressure on clusters with many collections or large documents. This pressure can degrade performance or destabilise the cluster.

For recommended approaches and other ways to protect your production cluster, see [Schema discovery performance impact](https://docs.airbyte.com/integrations/sources/mongodb/mongodb-troubleshooting#schema-discovery-performance-impact) in the troubleshooting guide.

### MongoDB CDC limitations

MongoDB limits BSON documents to 16MB. During CDC syncs, change stream events for large documents can exceed this limit. This causes a `BSONObjectTooLarge` error. For resolution details, see [MongoDB CDC Limitations](https://docs.airbyte.com/integrations/sources/mongodb/mongodb-troubleshooting#mongodb-cdc-limitations) in the troubleshooting guide.
