# Agents need operating guardrails, not just better prompts.

As teams adopt agentic workflows, the governance challenge changes. The system
is no longer generating a single output in isolation. It is executing multi-step
work across tools, data, approvals, and business systems.

That changes the risk profile completely. An agent can look up data, trigger
systems, transform content, make recommendations, and pass work downstream. If
the organisation has not defined what is allowed, what must be checked, and
where accountability sits, the problem is no longer output quality alone. It is
operational behaviour.

## Why this is current now

The governance environment has caught up with the operational reality. In the
EU, AI Act enforcement powers began applying from 2 August 2026, transparency
obligations now matter for providers and deployers of generative systems, and
GPAI obligations have a staged compliance timetable. ISO/IEC 42001 also gives
organisations a management-system pattern for responsible AI use, while NIST's
AI RMF remains a practical reference for mapping, measuring, managing, and
governing risk.

That does not mean every brand workflow is a regulated high-risk AI system. It
does mean serious organisations need evidence, ownership, and repeatable control
before agents become normal operating infrastructure.

## Where brand risk appears
- Tool selection (which systems are allowed for which tasks).
- Data access (what brand assets can be fetched and used).
- Output validation (what must be checked before publish).
- Auditability (what happened, when, and why).

The same pattern applies beyond marketing. Service teams, sales operations, internal support, and risk functions all need agents to stay inside governed boundaries. The interface may be different, but the control problem is the same.

## A policy-aware agent pattern
1. **Plan**: agent proposes steps and required assets.
2. **Authorize**: policy checks what is permitted.
3. **Execute**: actions happen with logging.
4. **Validate**: outputs are checked against brand policy.
5. **Escalate**: uncertain cases go to a human owner.

## Where MCP and the implementation layer fit
This is where governed infrastructure matters. In our model, the implementation layer acts as the controlled communications layer and MCP servers provide structured access to tools, policies, and knowledge. That allows the organisation to mediate agent behaviour rather than hoping prompts will be enough.

A well-designed MCP layer can do things such as:

- validate whether the agent is allowed to call a tool
- resolve which policy bundle applies in context
- restrict which assets or datasets can be used
- enforce post-execution checks before release or escalation
- log the full decision path for review

The result is not simply “safer prompts”. It is an agent workflow that can be governed, audited, and improved over time.

<Note>
Policy-aware tooling can be expressed as an MCP layer that enforces governance before tools are called.
</Note>
